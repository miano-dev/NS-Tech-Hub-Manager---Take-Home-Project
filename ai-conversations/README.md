Examine the four CSV files, understand their structures, relationships, data types, and contents, and develop a Python script to perform a comprehensive quality and operational analysis of the sensor network. ### 1. Analyse the supplied CSV files

The four files are:
1. devices.csv – device registration and configuration information.
2. telemetry.csv – sensor transmission and gateway reception records.
3. gateway_status.csv – gateway operational status, battery, and backhaul information.
4. maintenance_log.csv – device maintenance and firmware update history.
Inspect the available columns and establish the relationships between the datasets using device identifiers, gateway identifiers, timestamps, and other relevant fields.
Do not assume that every optional measurement column is present. Handle missing values and unavailable measurements appropriately.
### 2. Develop a Python analysis script
Use Python, primarily with pandas and numpy, to create a reproducible analytical workflow.
The script should:
- Load and validate the four CSV files.
- Check for missing files and required columns.
- Parse timestamps correctly, using UTC for telemetry and gateway status records.
- Identify duplicate sensor transmissions.
- Distinguish unique device transmissions from multiple gateway receptions of the same transmission.
- Restrict the main analysis to the six-week deployment period, from 2 March 2026 to 12 April 2026 inclusive.
- Calculate device-level reporting and performance metrics.
- Evaluate battery and solar charging performance.
- Identify invalid sensor readings and suspicious GPS coordinates.
- Evaluate gateway connectivity and backhaul performance.
- Compare gateway-local message counts against detailed telemetry records.
- Examine firmware inconsistencies and maintenance records.
- Identify potential anomalies and assign appropriate severity levels.
- Calculate daily reporting completeness.

### 3. Device-level analysis
For every registered device, calculate:
- Total unique uplinks.
- Expected number of transmissions based on device type.
- Reporting completeness percentage.
- Median reporting interval.
- 95th-percentile reporting interval.
- Maximum reporting gap.
- First and last transmission timestamps.
- Minimum battery voltage.
- Initial and final battery voltage using first and last decile medians.
- Battery voltage change.
- Overall median solar charging current.
- Recent 15-day median solar charging current.
- Number of invalid sensor readings.
- First timestamp of an invalid sensor reading.
- GPS zero-coordinate occurrences for GPS collars.
- Rainfall observation statistics.
- Expected gateway reception share.
- Expected gateway median RSSI and SNR.
- Strongest receiving gateway and its median RSSI.

Use the following expected reporting intervals:

| Device type   | Expected interval |
| ------------- | ----------------- |
| soil_moisture | 15 minutes        |
| weather       | 15 minutes        |
| water_level   | 15 minutes        |
| gps_collar    | 60 minutes        |

Use the six-week deployment period to calculate expected reporting opportunities.

### 4. Gateway-level analysis

Evaluate each gateway using gateway status records and telemetry reception records.

Calculate:
- Number of observed hours.
- Number of offline hours.
- Number of backhaul-disconnected hours.
- Minimum and median gateway battery voltage.
- Median cellular RSSI.
- Number of messages received locally during backhaul outages.
- Number of detailed telemetry records available during those outages.
- Estimated missing detailed records.
- Percentage of local messages represented in detailed telemetry exports.

Do not confuse locally received messages with records successfully exported through the backhaul.

### 5. Anomaly detection
Develop transparent rules to identify potential issues, including:
- Reporting intervals significantly longer than expected.
- Low reporting completeness.
- Impossible sensor values exceeding an absolute value of 1,000,000.
- GPS collar coordinates of (0, 0).
- Battery declines of at least 0.15 V.
- Expected gateway reception shares below 30%.
- Rainfall sensors reporting only zero values despite at least 500 observations.
- Firmware versions that differ from the modal version within the same device model.
- Maintenance firmware updates that disagree with the registered device firmware.

Assign severity levels of critical, high, or medium as appropriate.

Each anomaly should include the device identifier, severity, anomaly category, and supporting evidence.

Treat these as candidate issues requiring human verification rather than definitive equipment diagnoses.

### 6. Daily reporting completeness

Generate a daily dataset for every supported registered device covering all 42 deployment days.

For each device and date, calculate:

- Expected uplinks.
- Actual unique uplinks.
- Daily reporting completeness percentage.

Include days with zero received messages so that reporting gaps are not hidden.
